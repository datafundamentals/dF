Workflow 1: Canonical Pattern

Production Google Sign-In + Emulator-Based Features
This is the recommended architecture for ALL apps in the DF monorepo.

  • Production-ready df-auth-wrapper component
  • Real Google OAuth flow (tests actual authentication)
  • Firestore, Storage, and Functions on emulators (fast development)
  • Clean separation: production auth + emulator features
  • Reusable pattern across all monorepo apps
  • Minimizes unnecessary differentiation

Workflow 2: Auth Emulator (Don't Copy!)

Firebase Auth Emulator with Custom UI
Proves emulator auth is possible, but it's an anti-pattern for our architecture.

  • Custom auth emulator UI (cute demo component)
  • Proves technical feasibility of emulator auth
  • Creates unnecessary differentiation between apps
  • Doesn't match production authentication flow
  • Known emulator auth limitations and issues
  • Use df-auth-wrapper instead!

Why show this? To demonstrate what NOT to do. It's valuable to understand that emulator auth is possible, but you should never replicate this pattern in production apps. Always use the canonical pattern (Workflow 1) instead.
